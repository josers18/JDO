# AGENTS.md — Snowflake_BoardEx_ExecIntel

Synthetic BoardEx / Equilar / ISS-style board director and executive intelligence dataset for the Cumulus FSC demo. One of 13. **Account-scoped with monthly cadence and an all-accounts audience (~36,813 anchors, PERSON + BUSINESS).** The v1 design was Commercial Banking only (~960 anchors); the rebroadcast dropped the `CLIENT_CATEGORY` predicate and added a PERSON-anchor "personal household" fallback row (see Gotchas).

> **v1.x multi-org-additive (Phase A, 2026-05-29 commit `c9119d32`).** Table now leads with `ORG_ID VARCHAR(18) NOT NULL DEFAULT 'JDO'` as the first column; PK promoted from `(ACCOUNT_ID, PROFILE_MONTH)` to `(ORG_ID, ACCOUNT_ID, PROFILE_MONTH)`. SP row factory stamps `"ORG_ID": anchor.get("ORG_ID", "JDO")` as the first key; MERGE source SELECT, ON, INSERT lists all lead with ORG_ID; UPDATE SET deliberately skips ORG_ID (PK-component, immutable). Backward-compatible — JDO loaders continue working unchanged via DEFAULT. Multi-org rollout runbook: `Snowflake_Cumulus_Common/docs/ROLLOUT.md`.

## Boundaries
- Owns: `DATA_JEDAIS.FINS__PUBLIC.BOARDEX_EXEC_INTEL`, `SP_GENERATE_BOARDEX_EXEC_INTEL`, `TASK_MONTHLY_BOARDEX_EXEC_INTEL`, and the DC Data Stream / DLO / DMO that federates this table.
- Does NOT own: `V_ACCOUNT_ANCHORS`, `MASTER_ACCOUNTS`, the seed/coverage helpers — see `Snowflake_Cumulus_Common`.
- Does NOT own any outbound Snowflake share. DC reads through via the existing "Snowflake (Federate / Zero Copy)" connector.
- **Account-scoped** — rows are keyed by composite PK `(ACCOUNT_ID, PROFILE_MONTH)`, with FK `ACCOUNT_ID` to `ssot__Account__dlm`. **1:1 — one row per distinct account per month.**

## Conventions
- The SP uses `cumulus_common.seed_for(...)` for determinism with salt `"boardex"` (**month-bucketed**, single-salt — no year-stable streams; matches Plan 8's simpler shape).
- **One seed stream per anchor per run** — `seed_for(account_id, "boardex", month_start)` where `month_start = run_ts.replace(day=1, hour=0, minute=0, second=0, microsecond=0)`. Drives BOARD_SIZE, BOARD_INDEPENDENCE_PCT, WOMEN_BOARD_PCT, MINORITY_BOARD_PCT, BOARD_AVG_TENURE_YEARS, GOVERNANCE_RATING, INTERLOCK_COUNT, KEY_DIRECTOR_NAME, RECENT_GOVERNANCE_EVENT_DATE, LAST_DATA_REFRESH_DATE. Mid-month re-runs are byte-identical because `month_start` truncates day + time.
- **Second, account-lifetime seed stream for the C-suite timeline** — `seed_for(account_id + "_csuite", "boardex", datetime(2000, 1, 1))`. Drives CEO_TENURE_YEARS and EXEC_TURNOVER_FLAG (see Gotchas → "C-suite timeline"). It never depends on the profile month or run_ts, so every month reads the same timeline.
- The SP uses `cumulus_common.assert_coverage(session, expected_sql, actual_sql)` for the standard 1:1 audience-vs-actual coverage check — distinct accts = audience (every distinct anchor must produce exactly one row per month).
- The MERGE replaces on composite PK `(ORG_ID, ACCOUNT_ID, PROFILE_MONTH)`. Re-runs same calendar month are idempotent (byte-identical). Re-runs in a later month INSERT new rows for that month.
- Audience SQL is `SELECT DISTINCT * FROM V_ACCOUNT_ANCHORS` — no predicate; `_anchor_in_audience` is True iff `ACCOUNT_ID` is non-empty. ~36,813 distinct accounts. The v1 predicate `WHERE CLIENT_CATEGORY = 'Commercial Banking'` (960 accounts, probed 2026-05-28) is gone. BUSINESS anchors drive the `EMPLOYEE_COUNT` / `INTERLOCK_DEGREE` bias bands; PERSON anchors (NULL `EMPLOYEE_COUNT`) take the personal-household fallback.
- `accounts_processed` in `TASK_EXECUTION_LOG` equals `len(audience)` — the **distinct customer count** AND the row count (1:1 emit per anchor per month).

## Tests
- L1 (pytest): determinism in the same calendar month (byte-identical at 03:00 vs 23:30, day-1 vs day-15), input-shape validation (ACCOUNT_ID non-empty), boring case (mid-market enterprise: ~2,500 employees, INTERLOCK_DEGREE=2 → BOARD_SIZE 8-10, GOVERNANCE_RATING `Strong` or `Adequate`, EXEC_TURNOVER_FLAG mostly False, RECENT_GOVERNANCE_EVENT_DATE NULL ~70% of the time), **per-anchor range invariants** (BUSINESS rows; every row's BOARD_SIZE in [5,15]; BOARD_INDEPENDENCE_PCT, WOMEN_BOARD_PCT, MINORITY_BOARD_PCT all in [0.0,100.0]; BOARD_AVG_TENURE_YEARS in [1.0,20.0]; CEO_TENURE_YEARS in [0.0,25.0]; INTERLOCK_COUNT in [0,5]), **per-row vocabulary invariants** (GOVERNANCE_RATING in `{Excellent, Strong, Adequate, Weak, Concerning}`; EXEC_TURNOVER_FLAG is a Python `bool`), **date-coherence invariants** (LAST_DATA_REFRESH_DATE ≤ run_ts.date(); when populated, RECENT_GOVERNANCE_EVENT_DATE ≤ run_ts.date()), **bias-band invariants** (EMPLOYEE_COUNT≥10000 → BOARD_SIZE≥9 always; EMPLOYEE_COUNT<100 → BOARD_SIZE≤8 always; INTERLOCK_DEGREE≥4 → INTERLOCK_COUNT≥2 always), schema contract (16 keys per dict; KEY_DIRECTOR_NAME is non-empty `"<First> <Last>"`). **Turnover-timeline properties (2026-11-02):** determinism (incl. after `cache_clear`), timeline stable across 36 run_ts, stickiness (rise at M ⇒ TRUE M..M+11), stays ≥ 8× rises, TRUE rate in [15%, 25%] over 1,200 live-band-mix anchors × 36 months, large-firm rate < small-firm rate, CEO tenure monotone between CEO changes (resets < 1.0 with flag TRUE), CEO_TENURE_YEARS 1-dp in [0, 25].
- **L1 conftest (all-accounts).** `in_audience_anchors` returns the full `SAMPLE_ANCHORS` slice; `out_of_audience_anchors` returns `[]` — the only out-of-audience case is an empty `ACCOUNT_ID`, built inline per test. The inline 5-anchor `COMMERCIAL_BANKING_FIXTURE` (mid-market enterprise / regulated bank / family business / recent IPO / large cap) is kept as the `commercial_banking_fixture` fixture for the enterprise bias-band tests, because the 100-anchor `SAMPLE_ANCHORS` slice still has zero Commercial Banking BUSINESS anchors. PERSON anchors are covered by a personal-household property test.
- L2 (`tests/integration/`): deploys a clone of the SP against `V_ACCOUNT_ANCHORS_BOARDEX_FIXTURE` (14 anchors, all in audience: 5 Commercial Banking BUSINESS + 9 `NCB-` — 7 PERSON, 2 BUSINESS); asserts coverage (`COUNT(DISTINCT ACCOUNT_ID) = 14`, `COUNT(*) = 14`), all 9 `NCB-` anchors present, PERSON rows match the personal-household fallback shape, `BOARD_SIZE` in [5,15] for BUSINESS rows only, NOT NULL columns populated, range and vocabulary invariants as in L1, 0 future-dated LAST_DATA_REFRESH_DATE / RECENT_GOVERNANCE_EVENT_DATE, idempotency on same-month re-run (ROWS_INSERTED=0, hash unchanged).
- L3 (manual smoke, post-deploy): one CALL against jdo-uqj0jr; row count ≈ 36,813 (distinct accounts); 5-row sample plausibility (mix of governance ratings); GOVERNANCE_RATING distribution skewed toward Strong / Adequate; range invariants (BOARD_SIZE in [5,15]; independence/diversity pcts in [0,100]; etc.); vocabulary all in canonical 5-value set; 0 future-dated LAST_DATA_REFRESH_DATE; 0 future-dated RECENT_GOVERNANCE_EVENT_DATE when populated; RECENT_GOVERNANCE_EVENT_DATE populated rate ≈ 30% (target 30%, tolerance ±5%).

## Gotchas
- **C-suite timeline (EXEC_TURNOVER_FLAG / CEO_TENURE_YEARS, fixed 2026-11-02).** The rowspec defines the flag as "any C-suite change in the trailing 12 months", so it must be sticky. Until 2026-11-02 both fields were re-drawn iid every month from the monthly rng. Live pre-fix numbers on BUSINESS rows, 2024-06 → 2026-11: 49,962 FALSE→TRUE rises, 12,457 TRUE→TRUE stays, 49,941 TRUE→FALSE falls. Now `_csuite_timeline(account_id, band)` builds one lifetime event list per BUSINESS anchor:
  - Per-firm mean CEO tenure is drawn from an EMPLOYEE_COUNT band (≥10k: 8-16y, ≥1k: 6-13y, else 4.5-13y).
  - CEO changes arrive with exponential gaps, each clamped to [0.25, 22] years.
  - Other C-suite departures (CFO, COO, CRO, CTO, CIO, GC) arrive at 0.8× the CEO rate.
  - The timeline runs 2000 → 2030.

  `_exec_state_for_month` then reads it: flag = any event in `(month_end(M-12), month_end(M)]`, tenure = years since the last CEO change. Properties:
  - A rise at M stays TRUE through M+11.
  - The flag is ~20% TRUE. Projected numbers come from an offline replay of the deployed SP logic over the live `V_ACCOUNT_ANCHORS` audience (36,949 anchors, 10,864 BUSINESS) for 2024-06 → 2026-11, run 2026-11-02: monthly TRUE rate 19.85%-21.12% (20.55% overall), 4,682 rises / 60,110 stays / 4,673 falls (stays ≈ 12.8× rises), 0 stickiness violations out of 2,929 checkable rises. Projected per band: <1k 20.6%, 1k-9,999 16.1%, ≥10k 20.6%. The ≥10k band has only 17 live anchors, so the "large firms run lower" bias is a population-average property enforced by L1, not something to read off the live ≥10k band.
  - **Live re-run status: DONE 2026-11-02 — live data is sticky.** `CALL DATA_JEDAIS.FINS__PUBLIC.SP_GENERATE_BOARDEX_EXEC_INTEL(30, TRUE)` ran 2026-11-02 at about 15:36 PST as ACCOUNTADMIN (table LAST_ALTERED 15:39 PST). Those rows contribute no transitions.

  - Large firms run lower on average.
  - A CEO change resets tenure below 1.0 and forces the flag TRUE.

  The pair no longer consumes the monthly rng, so later draws in each row (governance-rating noise, interlocks, director name, dates) shifted once when this landed. PERSON rows are unchanged (flag False, tenure 5.0). `_csuite_timeline` is `lru_cache`d so the 30-month re-run builds each timeline once.
- **SP signature: `SP_GENERATE_BOARDEX_EXEC_INTEL(NUM_MONTHS INT DEFAULT 1, HISTORY_UPDATE_ONLY BOOLEAN DEFAULT FALSE)`** (2-arg since 2026-11-02; `deploy_sp.py` drops the old `(NUMBER)` overload first so the TASK's `CALL ...()` is never ambiguous). `HISTORY_UPDATE_ONLY=TRUE` regenerates past months **in place**: those MERGEs have no `WHEN NOT MATCHED`, so anchors that joined the audience later don't get back-filled rows. The current month always runs the full MERGE. To re-apply a logic change to the whole live history (2024-06 → present = 30 months on 2026-11-02), run `CALL DATA_JEDAIS.FINS__PUBLIC.SP_GENERATE_BOARDEX_EXEC_INTEL(30, TRUE);`. The SP generates and MERGEs one month per batch (~37K rows) to bound memory.
- **Band crossing breaks continuity.** `_csuite_timeline` is keyed on `(account_id, band_floor)`, and the band sets the per-firm mean tenure. `EMPLOYEE_COUNT` comes from CRM (`ssot__EmployeeCount__c`). If an account's count crosses 1k or 10k, its whole timeline is regenerated, and the monthly run (current month only) can then produce a spurious rise/fall or a CEO-tenure jump against stored history. This is accepted: band crossings are rare in this demo org, and a `(N, TRUE)` re-run realigns the history.

WHERE ORG_ID='JDO' AND ACCOUNT_ID='001am00000qvjs6AAA' AND PROFILE_MONTH='2026-10-01'`; `DELETE` that key; `INSERT ... - **Partial history on mid-run failure.** Multi-month runs generate and MERGE one month at a time. A failure part-way through (for example a row-factory tolerance breach) leaves the earlier months rewritten and the later ones untouched. The run is idempotent, so re-running the same CALL repairs it.
- **Run accounting.** `TASK_EXECUTION_LOG.ROWS_INSERTED` counts INSERTs only. An update-only history re-run logs ~0 inserted, and the SP return string reports `updated=<n>` separately.
- **RECORD_ID.** The live table has `RECORD_ID VARCHAR(36) NOT NULL DEFAULT UUID_STRING()`. The SP computes the deterministic SQL form of `cumulus_common.record_id_for(ORG_ID, ACCOUNT_ID, PROFILE_MONTH)` in the MERGE source SELECT and writes it on INSERT and UPDATE. Rows inserted 2026-09 → 2026-11 before this change got random `UUID_STRING()` defaults (110,673 rows per the 2026-11-02 review), and the next MERGE touching them rewrites those to the deterministic value. The repo says DC reads through the Snowflake Federate / Zero Copy connector, so the rewrite should show up in place. If `BT_Boardex` is batch-ingested and keyed on RECORD_ID, though, the old IDs would linger as duplicates and need a full refresh. The ingest mode was not verified on 2026-11-02.
- **write_pandas target.** The staging table is written to `database="DATA_JEDAIS", schema="FINS__PUBLIC"`. The repo source said `FINS`/`PUBLIC` after the account migration, and the live SP had been hot-patched (the 2026-07-01 task failures were `Database 'FINS' does not exist`). Repo and live now agree.
- **Deploy connection.** `scripts/deploy_sp.py` runs unflagged `snow sql -f`. The deploy used `SNOWFLAKE_DEFAULT_CONNECTION_NAME=SFDC_DC_TECH_ARCH_jwt python scripts/deploy_sp.py`, which is still JWT, still unflagged, and opens no OAuth popup.

- **DC mapping.** No column changes, so the existing DC stream/DMO mapping (`BT_Boardex__dlm`) is unchanged. Status for any new DC work: DC mapping pending UI.
- **All-accounts audience (rebroadcast).** ~36,813 anchors; v1 was the smallest Cumulus audience (960, Commercial Banking only). Per-anchor invariants stay load-bearing — BUSINESS and PERSON rows follow different contracts, so BUSINESS-only range checks (e.g. `BOARD_SIZE` in [5,15]) must be scoped to BUSINESS rows.
- **PERSON-anchor "personal household" fallback.** PERSON anchors have no board, so the SP emits: `BOARD_SIZE = 1`, `BOARD_INDEPENDENCE_PCT = 100.0`, `WOMEN_BOARD_PCT` / `MINORITY_BOARD_PCT` in `{0.0, 100.0}` (deterministic from `ACCOUNT_ID` hash), `BOARD_AVG_TENURE_YEARS = CEO_TENURE_YEARS = 5.0`, `EXEC_TURNOVER_FLAG = False`, `GOVERNANCE_RATING = 'Adequate'`, `INTERLOCK_COUNT = 0`, `KEY_DIRECTOR_NAME = 'Self'`, `RECENT_GOVERNANCE_EVENT_DATE = NULL`.
- **Per-anchor deterministic invariants, not distributional.** Property tests for range / vocabulary / bias-band / date-coherence are per-anchor or per-row (e.g. "every EMPLOYEE_COUNT≥10000 anchor has BOARD_SIZE≥9"), NOT mean comparisons or rate convergence. Plans 1-7 leaned on rate-convergence over SAMPLE_ANCHORS; Plan 8 first shifted to per-anchor invariants because the cohort was too narrow; Plan 10 takes that shift further because the cohort isn't even sampled in SAMPLE_ANCHORS.
- **Single NULLable column with independent NULL draw.** `RECENT_GOVERNANCE_EVENT_DATE` is NULL ~70% of rows via a flat 30%/70% Bernoulli draw — *no* multi-column coordination needed. Simpler than Plan 8's PLAN_STATUS-gated 2-NULL setup. The DDL marks it as NULL; the MERGE source SELECT must preserve `None` → `NULL`.
- **Anchor reads.** `EMPLOYEE_COUNT` (drives BOARD_SIZE bands and CEO_TENURE_YEARS bands) and `INTERLOCK_DEGREE` (drives INTERLOCK_COUNT). Populated for BUSINESS anchors; PERSON anchors (NULL `EMPLOYEE_COUNT`) take the personal-household fallback instead.
- **Date-coherence invariants** (must hold per row, asserted in L1 and L3):
  - `LAST_DATA_REFRESH_DATE ≤ run_ts.date()` — always, drawn 1-30 days ago.
  - `RECENT_GOVERNANCE_EVENT_DATE` (when populated) `≤ run_ts.date()` — drawn 1-365 days ago, no future-dated events.
- Salt is `"boardex"` (monthly cadence, single-salt). No year-stable subfield (board structure / governance rating / interlock count / dates are all month-bucketed).
- 1 BOOLEAN column (`EXEC_TURNOVER_FLAG`) — declare as `Boolean` in DC DLO + DMO (Plan 5 / Plan 8 finding — defaulting to Text fails the Boolean parse). Snowflake stores BOOLEAN natively; the MERGE source SELECT casts via `EXEC_TURNOVER_FLAG::BOOLEAN` to be explicit (write_pandas could mis-type on an empty target).
- 1 NULLable date column (`RECENT_GOVERNANCE_EVENT_DATE`) — independent 30% Bernoulli, no enum gating.
- The `write_pandas(auto_create_table=True)` mis-types `datetime64[ns]` as `NUMBER(38,0)`. The MERGE source SELECT casts back via `TO_TIMESTAMP_NTZ(GENERATED_AT::NUMBER / 1000000000)` — see template Task 4 §_merge.
- 14 columns total: 13 NOT NULL + 1 NULLable (RECENT_GOVERNANCE_EVENT_DATE). 1 BOOLEAN NOT NULL.
- The DLO → DMO field mapping must be completed in DC Setup UI for fully-custom DMOs (the API endpoint returns 500). See the recipe at `../Snowflake_Claritas_Demographics/docs/dc-setup-recipe.md` from Plan 1 T7.
- Snowflake DATE columns auto-discover as `MM/dd/yyyy` in the DC data-stream POST body. Use that format for `PROFILE_MONTH`, `RECENT_GOVERNANCE_EVENT_DATE`, `LAST_DATA_REFRESH_DATE`'s `sourceFields` entries, NOT `yyyy-MM-dd`.
- DC mapping descriptions must be ≤521 chars (Plan 6 finding). Trim the DMO description if drafting against the rowspec verbatim.
- "BoardEx" / "Exec Intel" are both clean — no `&` sanitize gymnastics needed (compare Plan 6's `D&B` workaround).
- `accounts_processed = len(audience) = row count` (1:1 emit per anchor per month) — same shape as Plans 1-3, 5, 7, 8.
- Cadence is **monthly** (`'USING CRON 0 3 1 * * America/New_York'`, the live schedule; the repo task file was synced to it 2026-11-02 and previously said `0 7 1 * * UTC`).
- **Volume.** ~36,813 rows/month. Re-runs same month MERGE-replace in place; live storage grows by ~36,813 rows per month.
