# AGENTS.md — Snowflake_WorldCheck_AML

Synthetic LSEG World-Check / Dow Jones Risk & Compliance / ComplyAdvantage-style AML / sanctions / PEP screening dataset for the Cumulus FSC demo. One of 13. **Account-scoped with daily cadence — first daily-cadence dataset AND first all-accounts-audience dataset in the rollout.**

> **v1.x multi-org (Phase A 2026-05-29 `c9119d32`; deployed SQL ported 2026-11-09, PR #168).** Live table: PK `RECORD_ID` (`UUID_STRING()` default, the row id the DMO keys on); UNIQUE `(ACCOUNT_ID, PROFILE_DATE)` (`RELY = false`, not enforced, no `ORG_ID`, which is cosmetic); `ORG_ID VARCHAR(18)` nullable, `DEFAULT 'JDO'`, second-to-last column. Both `procedures/sp_generate_*.py` and the deployed `procedures/sp_create_procedure.sql` stamp `"ORG_ID": anchor.get("ORG_ID") or "JDO"` on each row, and the MERGE source SELECT, `ON` and `INSERT` carry `ORG_ID`, so `(ORG_ID, ACCOUNT_ID, PROFILE_DATE)` is the effective key. UPDATE SET skips `ORG_ID` (key component). World-Check's explicit audience column list includes `ORG_ID`, and its latest-snapshot `QUALIFY` partitions by `(ORG_ID, ACCOUNT_ID)`. Multi-org rollout runbook: `Snowflake_Cumulus_Common/docs/ROLLOUT.md` (A6).

## Boundaries
- Owns: `DATA_JEDAIS.FINS__PUBLIC.WORLD_CHECK_AML`, `SP_GENERATE_WORLD_CHECK_AML`, `TASK_DAILY_WORLD_CHECK_AML`, and the DC Data Stream / DLO / DMO that federates this table.
- Does NOT own: `V_ACCOUNT_ANCHORS`, `MASTER_ACCOUNTS`, the seed/coverage helpers — see `Snowflake_Cumulus_Common`.
- Does NOT own any outbound Snowflake share. DC reads through via the existing "Snowflake (Federate / Zero Copy)" connector.
- **Account-scoped** — rows are keyed by `(ORG_ID, ACCOUNT_ID, PROFILE_DATE)` (MERGE `ON`; table PK is `RECORD_ID`), with FK `ACCOUNT_ID` to `ssot__Account__dlm`. **1:1 — one row per distinct account per screening day.**

## Conventions
> **Live algorithm (synced from GET_DDL 2026-11-09).** The original rowspec (30 jurisdictions in Standard / Enhanced / Prohibited tiers, year-stable seeds, `WCH-` case IDs, five change values) was never what shipped. `procedures/sp_generate_world_check_aml.py` now matches the deployed body, and the bullets below describe it.

- **Daily seed** — `_daily_seed(account_id, day_start)` = sha256 of `f"{account_id}|worldcheck|{day:%Y-%m-%d}"`. Drives the daily flag flips and the adverse-media category. Mid-day re-runs are byte-identical because `day_start` truncates the time.
- **Month-stable seeds** — everything else goes through `cumulus_common.seed_for`, which buckets by **year-month** (not year, whatever the in-code comments say): jurisdiction (`worldcheck_jurisdiction`), the base hit flags (`worldcheck_<flag>`), the noise bump (`worldcheck_noise`) and CASE_REFERENCE (`worldcheck_case`). They are stable within a calendar month and re-drawn on the 1st (36,833 accounts changed jurisdiction from September to October 2026).
- Each hit flag = month-stable base XOR a ~0.3% daily flip; flags are 0/1 ints that the MERGE casts with `::BOOLEAN`. Marginal rates: sanctions ~0.5%, PEP ~1.2%, adverse media ~3.0%.
- The SP uses `cumulus_common.assert_coverage(session, expected_sql, actual_sql)` for the standard 1:1 audience-vs-actual coverage check (every distinct anchor must produce exactly one row per screening day).
- The MERGE replaces on `(ORG_ID, ACCOUNT_ID, PROFILE_DATE)`. Re-runs same calendar day are idempotent (byte-identical). Re-runs on a later day INSERT new rows for that day's screening.
- Audience SQL selects an explicit column list (including `ORG_ID`) from `V_ACCOUNT_ANCHORS` with **no WHERE clause** (first all-accounts plan) and `QUALIFY ROW_NUMBER() OVER (PARTITION BY ORG_ID, ACCOUNT_ID ORDER BY SNAPSHOT_DATE DESC) = 1`, so each account appears once.
- 13-jurisdiction pool `_JURISDICTIONS` in four tiers (Low / Medium / High / Prohibited), drawn **uniformly** per account per month. 2 of the 13 are Prohibited and Prohibited → Severe, so ~15% of rows are Severe (15.85% on 2026-11-09). NOT license-grade vendor data.
- `accounts_processed` in `TASK_EXECUTION_LOG` equals `len(audience)` — the **distinct customer count** AND the row count (1:1 emit per anchor per day).

## Gotchas
- **Daily cadence.** `PROFILE_DATE` is a DATE column equal to `day_start.date()`, NOT `PROFILE_MONTH`/`PROFILE_QUARTER`. The seed bucket is day-start `datetime(year, month, day, 0, 0, 0)` — mid-day re-runs are byte-identical because the time component is truncated. Plans 1-3, 6 use month-bucketing; Plan 5 uses quarter-bucketing; Plan 7 introduces day-bucketing for the first time.
- **All-accounts audience.** No `WHERE` predicate beyond `SELECT DISTINCT *`. **`_anchor_in_audience(anchor)` always returns `True`** — there is no filter cohort. Don't reintroduce a CLIENT_CATEGORY or ACCOUNT_TYPE_FLAG check; AML is non-negotiable for every customer (legal posture). Plan 4's `POSTAL_CODE <> ''` filter doesn't apply; Plan 5's PERSON-only filter doesn't apply; Plan 6's `CLIENT_CATEGORY IN (...)` filter doesn't apply.
- **Anchor-independent bias.** The row factory reads ONLY `anchor["ACCOUNT_ID"]` — NO BIRTHDATE / ANNUAL_INCOME / STATE / CLIENT_CATEGORY / POSTAL_CODE / ZIP. Even `RISK_JURISDICTION_CODE` is **synthesized** (month-stable salt `worldcheck_jurisdiction`) instead of read from the dirty `anchor.COUNTRY_CODE` field (96% `US` + 30% empty/dirty per Plan 0 probe — no signal). This is a structural deviation from Plans 1-6 where the row factory inspects multiple anchor fields for bias. Don't reintroduce demographic reads here — they are not available signals.
- **Month-stable, not year-stable.** `seed_for` buckets by year-month, so jurisdiction, base flags, noise and CASE_REFERENCE re-draw each month. If year-stability is wanted, bucket by `datetime(run_ts.year, 1, 1)` before calling `seed_for` and regenerate the history; don't just edit the comments.
- **3 BOOLEAN columns.** `SANCTIONS_HIT`, `PEP_HIT`, `ADVERSE_MEDIA_HIT` — all NOT NULL. DC needs explicit `Boolean` declaration in the DLO + DMO field input for ALL THREE (Plan 5 finding — defaulting to Text fails the Boolean parse). Snowflake stores BOOLEAN natively; the MERGE source SELECT casts via `SANCTIONS_HIT::BOOLEAN`, `PEP_HIT::BOOLEAN`, `ADVERSE_MEDIA_HIT::BOOLEAN` to be explicit (write_pandas could mis-type on an empty target).
- **2 NULLable columns.** `ADVERSE_MEDIA_CATEGORIES` is NULL when `ADVERSE_MEDIA_HIT=false` (~97% of rows), and also on some hits, because `_MEDIA_CATS` includes `None` (4,939 media-hit rows with NULL categories in the 30 days to 2026-11-09). `CASE_REFERENCE` (`WC-YYYY-NNNNN`) is NULL when `OVERALL_RISK_RATING NOT IN ('High', 'Severe')`. About 6,071 old `WCH-` refs from early runs remain in history. The DDL marks both as NULL; the MERGE source SELECT must preserve `None` → `NULL`.
- **CHANGE_SINCE_LAST_RUN re-derives yesterday.** `_change_since_last_run` recomputes yesterday's rating from yesterday's seeds and returns only `Changed` or `Unchanged` (the docstring's `New` is never emitted). Keep the flag / rating helpers pure so they can run twice.
- Salt is `"worldcheck"` for the daily seed; `worldcheck_jurisdiction`, `worldcheck_case`, `worldcheck_<flag>` and `worldcheck_noise` for the month-stable fields.
- Cadence is **daily** (`'USING CRON 0 6 * * * UTC'` — 06:00 UTC daily, after LSEG's overnight feed publishes at ~02:00 GMT).
- The `write_pandas(auto_create_table=True)` mis-types `datetime64[ns]` as `NUMBER(38,0)`. The MERGE source SELECT casts back via `TO_TIMESTAMP_NTZ(GENERATED_AT::NUMBER / 1000000000)` and `TO_TIMESTAMP_NTZ(LAST_SCREENED_AT::NUMBER / 1000000000)` — see template Task 4 §_merge.
- **Deploy under ACCOUNTADMIN.** `python3 scripts/deploy_sp.py` regenerates `procedures/sp_create_procedure.sql` and creates the SP `EXECUTE AS OWNER` as ACCOUNTADMIN (`write_pandas` staging needs CREATE TABLE in `DATA_JEDAIS.FINS__PUBLIC`).
- 15 columns total: 12 NOT NULL (RECORD_ID, ACCOUNT_ID, PROFILE_DATE, OVERALL_RISK_RATING, SANCTIONS_HIT, PEP_HIT, ADVERSE_MEDIA_HIT, RISK_JURISDICTION_CODE, RISK_JURISDICTION_TIER, LAST_SCREENED_AT, CHANGE_SINCE_LAST_RUN, GENERATED_AT) + 3 NULLable (ADVERSE_MEDIA_CATEGORIES, CASE_REFERENCE, ORG_ID).
- L1 conftest provides a synthetic anchor fixture — `SAMPLE_ANCHORS` from Cumulus_Common with `in_audience_anchors = all_anchors` (everyone is in audience; no filter step in the L1 helper).
- The DLO → DMO field mapping must be completed in DC Setup UI for fully-custom DMOs (the API endpoint returns 500). See the recipe at `../Snowflake_Claritas_Demographics/docs/dc-setup-recipe.md` from Plan 1 T7.
- Snowflake DATE columns auto-discover as `MM/dd/yyyy` in the DC data-stream POST body. Use that format for `PROFILE_DATE`'s `sourceFields` entry, NOT `yyyy-MM-dd`.
- DC mapping descriptions must be ≤521 chars (Plan 6 finding). Trim the DMO description if drafting against the rowspec verbatim.
- `accounts_processed = len(audience)` matches row count (1:1 emit per anchor per day) — unlike Plan 6 where `accounts_processed ≠ row_count` (1:N).
- **Volume.** One row per anchor per day (36,953 anchors on 2026-11-09). Same-day re-runs MERGE-replace in place, and each new day adds a full set, so history accumulates: 5,860,286 rows across 159 screening days (2026-05-28 → 2026-11-09).
