# Retail Atlas — action-to-client mapping

Reviewed November 13, 2026 against the checkout, not a fresh deployed-org write test. Companion to the [migration contract](RETAIL_MIGRATION_CONTRACT.md) and [acceptance register](RETAIL_PRODUCTION_ACCEPTANCE.md). This document specifies future integration; mock drafts still perform no bank writes.

All CRM execution uses `force-app/main/default/uiBundles/_shared/src/data/crmWriteClient.ts` (`crmWrite`) → SDK `fetch('/services/apexrest/crm/write')` → `CrmWriteRest.cls`. Normalize a typed proposal to an allowlisted `CrmWriteInput`; never POST an entire study draft. `original`, `plan`, `goalType`, `date`, `notes`, `signalKey` and readiness are mock/proposal fields, not automatically CRM API fields.

## Supported CRM operations

| User action | Payload / supported fields now | Exact association and refresh |
|---|---|---|
| Create task / follow-up / call preparation | `action:'task'`; subject, description, priority, status, dueDate, whoId, whatId. Current TaskModal sends a subset; the handler supports these fields. | Account or another supported related record → WhatId; exact Contact/Lead → WhoId. Owner currently defaults to actor. Refetch affected task/activity list and independent task count on success. |
| Edit task | `action:'update', sobjectType:'Task', recordId`; subject, status, priority, dueDate, type, description, whatId, ownerId. | Preserve source Task ID, recorded WhoId and unchanged assignee. Resolve Related To/Assigned To through actual lookups, not name/ID-shaped text alone. Refetch affected old/new customer contexts if links change. |
| Complete task | Same Task update with `status:'Completed'`; there is no separate `complete` bridge action. | Exact original Task, not a new completion Task. Preserve source metadata and refresh open-task/agenda counts. |
| Delete task | `action:'delete', sobjectType:'Task', recordId`. | Explicit delete operation on the exact source record; a saved delete proposal does not remove a task. Refetch after confirmed response. |
| Schedule meeting / call | `action:'event'`; subject, description, activityDateTime, durationMinutes, whoId, whatId. | Require an explicit reviewed start/timezone and duration in Atlas. Current handler defaults missing start to now+1h; do not present that default as a source appointment. New Event owner defaults to actor. |
| Edit meeting | `action:'update', sobjectType:'Event', recordId`; subject, activityDateTime, type, description, location, showAs, whatId, ownerId. | Keep source WhoId fixed; current update handler does not write duration. Preserve original Event/assignee unless changed explicitly. Refetch recorded agenda; do not put the update proposal into new-meeting planning. |
| Delete meeting | `action:'delete', sobjectType:'Event', recordId`. | Exact original Event. Keep proposal, success and refreshed calendar states distinct. |
| Create CRM service case | `action:'case'`; subject, description, priority, status, accountId. Handler sets Origin. | Exact Account link. No Case update/delete is supported by the current bridge allowlist. Refresh current CRM case count/list, not ServiceNow counts. |
| Send reviewed email | `action:'email'`; subject, toAddress, htmlBody (description fallback). `EmailModal` uses `accountLookup.fetchAccountEmail()` for actual recipient lookup and editable review. | No implicit WhoId/WhatId/email-activity linkage is written by this handler. Current result has null ID. Validate send result before claiming sent; never blindly retry an uncertain send or send an address-less recommendation. |
| Create financial goal | `action:'goal'`; name, type, financialPlanId; status defaults NOT_STARTED; priority, description, targetDate, targetAmount, actualAmount optional. | Customer link is FinancialPlan → Account. `goalType→type`, `plan→financialPlanId`, `notes→description`, amounts parse without turning blank into zero. Refresh plan/customer goals and goal totals. |
| Edit financial goal | `action:'update', sobjectType:'FinancialGoal', recordId`; name, status, priority, type, description, targetDate, targetAmount, actualAmount. | FinancialPlan is fixed for an existing goal. Zero amounts persist; blank update values generally leave source fields unchanged. No goal delete/reassignment route is supported. |
| Log life event | `action:'lifeEvent'`; name, primaryPersonId, eventType, eventDate. | Exact Contact, not Account. Input date is YYYY-MM-DD; current Apex anchors a DateTime at session-local midnight. Prove date round-trip across relevant timezones before release. |
| Edit life event | `action:'update', sobjectType:'PersonLifeEvent', recordId`; name, eventDate only. | Contact/type are create-time links; keep fixed and do not silently send ignored changes. No delete support. |
| Create Lead / referral proposal | `action:'lead'`; lastName and company required; firstName, status, leadSource, email, annualRevenue. | Lead is distinct from Account. AnnualRevenue is annual company revenue, not modeled banking revenue. Preserve blank versus zero and selected recorded picklist values. Refetch Lead list/count after confirmed insert. |
| Edit Lead | `action:'update', sobjectType:'Lead', recordId`; firstName, lastName, company, status, leadSource, email, annualRevenue. | Exact Lead ID; duplicate names stay distinct. No conversion/delete action is implemented by this bridge. |
| Graph suggestion → Lead | Same reviewed Lead-create payload after identity/contact review. | Referrer Account, external target Account, edge confidence/date stay separate provenance. Do not put a target Account in WhoId or treat a graph edge as consent/an existing Lead. No unique-referrer custom field is invented. |
| Create Opportunity from product evidence | `createWhitespaceOpportunity()` in `Shared/data/whitespace.ts` → `action:'opportunity'`; accountId, name, amount, leadSource, description, optional ownerId; server defaults Prospecting/+60d if stageName/closeDate absent. | `CrossSellWhitespaceLive` passes View As owner explicitly when previewing a banker. Preserve product label/name prefix and `Cross-sell grid` source, Account/product evidence and server ownership permission. Refetch native grid/outcome aggregates plus affected pipeline. |
| Generic new Opportunity | Same bridge create operation with reviewed name/accountId/amount/stageName/closeDate/description and supported source/owner. | An Opportunity create is supported; generic Opportunity edit, drag-to-stage update, close-won and delete are not supported by the present update allowlist. Keep planning gestures local unless an explicitly tested bridge extension is made. |

Task/Event create does **not** currently apply every update field: editable owner/type controls on create, or Event location/ShowAs on create, would silently overpromise. Current Event update similarly cannot change WhoId/duration. Constrain the form or extend the existing client/handler/tests before showing an editable supported capability. This is an integration choice, not proof that a field is inherently unavailable in Salesforce.

`CrmWriteInput.ownerId` is also honored for Opportunity creation despite its comment emphasizing Task/Event updates. Prefer inspected handler/helper behavior over stale comments. View As never changes the authenticated creator or permission context.

## Read-only and private design actions

| Design control | Intended binding / boundary |
|---|---|
| Search, stage/source/cohort filters, selected product/customer, pagination, Back | Router/history + scoped data clients. No CRM write. Live directories use proper scoped search/cursors; visible samples do not become totals. |
| Pin relationship | Existing WorkspaceSelection context, extended to org/user/persona identity keys; exact Account IDs. No bank-record mutation. |
| Snooze recommendation, readiness, private preparation, checklists | Scoped session proposal store. Do not complete/delete source records or claim dismissal of the live source issue. |
| Profile edits | Current bridge has no Account update operation. Keep a clearly local profile proposal or route to an explicitly supported existing platform edit experience after separate implementation. |
| Notebook / review packet / tearsheet preview | Private authored preparation; preserve actual Retail TearsheetBuilder/prompt flow where implemented. A composed packet is not generated model output or a saved Meeting_Note record. Source notes and local notes stay separate. |
| Source inspection / plot / screening | Exact source/customer/date lookup, with empty/unavailable/error states. Never mutate AML flags, external cases or hazard exposure from review controls. |
| ServiceNow follow-up | Create a Task on the exact customer Account; retain external case reference in reviewed context. No `SN-HOME-*` value in recordId/WhoId, and no claim that ServiceNow was updated. |
| Account/trade/transaction view | Source read only. No transfer, trading order or fabricated balance/return action. |
| Assistant launch/switch | Existing authenticated ACC mount/teardown/re-embed. Visible context label alone does not ground a conversation. An explicit supported record handoff must be proved separately. |
| AI rationale/prep/follow-ups/pipeline summary | Existing AI/prompt clients and configured action keys. Editable draft result only; require an explicit supported action to send/create anything. |
| Configuration / themes / display size | Existing config/theme clients and permissions. These are real settings writes in production, unlike the study's local preview. Per-center config and org theme definitions are not per-book settings. Active theme/display size use the authenticated user's map. |

## Validation, submission, failure and refetch

1. Resolve session actor/org, exact target IDs, supported operation, assignee permission, relevant current source evidence and active field metadata before enabling an executable request. Name matching, a 15/18-character shape or a local Ready flag is not sufficient authorization.
2. Normalize only supported fields; map proposal names explicitly. Keep optional undefined, blank and numeric zero distinct. Unknown source IDs, fields or enum values require a real lookup/metadata result or a useful unavailable state. Do not forward source-reference metadata as arbitrary writable CRM fields.
3. Use the existing write modal/useCrmAction behavior: pending button state, inline error without losing authored content, success-only callbacks. Tighten receipt validation where necessary: success:true with an ID for the expected object on insert; update/delete response ID must equal the exact requested recordId. Email requires its own confirmed-send result with no fabricated record ID. A merely shape-valid/non-null different ID is not success for the requested update/delete.
4. On 4xx/5xx or business failure, keep the form/draft and source links. On an ambiguous timeout, mark uncertain and reconcile before another attempt. Current bridge has no idempotency key; adding one requires an explicit supported implementation and tests. Email result inspection is an existing source limitation.
5. Call onSaved/refetch once after confirmed write. Refresh relevant live CRM list/aggregate, exact customer view and source outcomes. Keep unrelated views visible; identify mirrored source lag. If refresh fails after a confirmed write, preserve the success receipt and offer Retry refresh, not another Execute.
6. Keep read-after-write failure distinct from write failure. Do not optimistically increase the whole-book Closed Won/open-grid counts from a local draft or infer converted Leads from campaign clicks.

Current `HomePage.approveRec()` correctly routes recipient-less email recommendations to EmailModal. Other recommendation kinds can omit dates and use server defaults; Atlas must open scheduling review when a start is not explicit rather than invent an appointment in its agenda. The current quick paths remain on the retained layouts until their Atlas equivalent meets acceptance.
